## 1. The answers never enter the sandbox (fixes report 1.1, and makes 3.2 moot for the oracle)

Replace the in-container pytest oracle run with a Linus-owned driver:
- The container receives ONLY the imports and the call expressions (no expected values). A driver script
  (Linus-owned, mounted read-only, run as `python -I` with the PR's import root appended to sys.path AFTER the
  driver's own imports, as the suite run does) evaluates each call in its own fresh subprocess
  (`python -I` per case, with a per-case timeout), and each subprocess prints one JSON line:
  {"ok": true, "value": <result as JSON>, "plain": <bool: result and everything inside are exact plain JSON types,
  no subclasses, dict keys str>} or {"ok": false, "error": "<ExceptionType>: <message>", "where": "<file of the
  deepest frame>"}.
- The HOST (Linus process, never imports PR code) compares each result with the expected value: pass only if
  ok and plain and json.dumps(value, sort_keys=True) == json.dumps(expected, sort_keys=True); raises cases pass only
  if the error type name matches. Missing/garbled lines = failed case. Forging now requires knowing the expected
  value, which never left the host.
- Keep the oracle's own text representation (the rendered pytest file) for receipts/readability if useful, but
  the verdict must come from the host-side comparison. Oracle validation on base uses the same driver: a case
  reproduces the bug if it fails on base for a real reason (decide by LOCATION first, report 3.5: deepest frame
  under the PR/base tree's package = reproduction; in the driver/case expression, stdlib or site-packages =
  authoring error), and `linus receipt` re-verification must still work.
- Bump oracle FORMAT, record the format on each item's oracle record and on the run (report 3.6); on resume refuse
  runs judged under an older format with a clear message.
